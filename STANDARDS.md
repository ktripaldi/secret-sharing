# Engineering Standards (React / TypeScript)

This document is a reusable, project-agnostic reference for engineering standards in any React + TypeScript codebase. Adopt it wholesale, or fork the sections you need. Wherever it says "your project," substitute the concrete tool, path, or convention your repo actually uses, and codify that choice once so the whole team follows it.

The standards assume a modern stack — TypeScript in strict mode, React (with or without a framework like Next.js / Remix / Vite), a schema validator (Zod or equivalent), a data-fetching layer (TanStack Query or equivalent), a test runner (Vitest / Jest), and an E2E tool (Playwright / Cypress). Where a standard names a specific tool, it's an example; the principle is what matters.

## 1. Quality

Quality standards govern type safety, correctness, and the prevention of subtle defects.

### 1.1 TypeScript Strictness

- **Strict mode is mandatory.** Enable `"strict": true` in your base `tsconfig`. Also turn on `"noUncheckedIndexedAccess"`, `"noImplicitOverride"`, and `"isolatedModules"`. Apps and packages extend one shared base config — they never relax `strict`.
- **No `any` in production code.** Use `unknown`, proper generics, or types generated by your ORM/schema layer. If a third-party type gap forces a cast, isolate it behind a typed wrapper. Test files are the only acceptable place for the occasional `as any` against an awkward mock shape.
- **No non-null assertions (`!`) on external/untrusted values** — environment variables, query params, API responses. Validate with an early guard that narrows the type. Reserve `!` for cases the compiler genuinely can't see but you can prove.
- **Let the compiler infer.** Don't hand-annotate what an ORM `select`/`include`, a Zod `infer`, or a return type already gives you. Annotate public API boundaries; infer internals.
- **Use function overloads** when a function has multiple legitimate call signatures, so callers can't mix incompatible argument shapes.
- **Discriminated unions over flag bags.** Model "one of N shapes" as a tagged union, not an object with many optional booleans. Derive constant sets with `as const` and `(typeof X)[keyof typeof X]` to get autocomplete and typo-proofing.

### 1.2 Linting and Build Gates

- **Lint and build must pass with zero errors and zero warnings** before work is considered complete. No "I'll fix it later." Run lint with `--max-warnings 0`.
- **Typecheck runs across the whole workspace**, not just the app you touched — shared types ripple.
- ESLint extends a recommended baseline (e.g. `eslint:recommended` + `@typescript-eslint` + framework rules such as `next/core-web-vitals` or `react-hooks`). Generated and vendored files are explicitly ignored.
- **Format with a single formatter** (Prettier or equivalent) wired into the editor and CI. Formatting is never a review topic — the tool decides.
- **Pre-commit hooks** run lint + typecheck on staged files (Husky + lint-staged, or equivalent).

### 1.3 Input Validation at Boundaries

- **Every external input is validated with a schema** (Zod or equivalent) before any business logic touches it — request bodies, query params, webhook payloads, form submissions, and data crossing a trust boundary.
- **Strip unknown keys, don't pass them through.** Use the validator's "strip" mode on top-level schemas so callers can't inject unexpected fields into a downstream write.
- **Normalize quirky inputs at the validation boundary** with schema transforms (e.g. empty-string → undefined), rather than scattering normalization through business logic.
- **Validation failures return a structured 4xx** with machine-readable details, never a 500. Derive your TypeScript types from the schema (`z.infer`) so the validated shape and the static type can't drift.

### 1.4 Data-Layer Query Quality

- **Push aggregation down to the data store.** Use the database's `count`/`groupBy`/`aggregate` rather than fetching all rows and reducing in JS. Parallelize independent queries (e.g. a page of rows + a total count) with `Promise.all`.
- **Select only the columns you need.** Never fetch the whole row by default when a handful of fields will do.
- **Whitelist anything that names a column.** Sort fields, filter fields, and `orderBy` keys from a query string must be validated against an allow-list, never interpolated directly — this is both a correctness and an injection concern.
- **Pagination is mandatory on list endpoints.** Clamp page size: `Math.min(MAX, Math.max(1, requested))`. Never return an unbounded result set to a client.
- **Scope every multi-tenant query by tenant.** If your app serves multiple tenants/orgs/users, every query against a tenant-scoped table must include the tenant key in its `where` clause. Cross-tenant leakage is the highest-severity bug class in any multi-tenant app.

### 1.5 Error Handling

- **Centralize error-to-response mapping.** Write one helper that maps known error types to HTTP statuses (auth → 401, forbidden → 403, validation → 400, conflict → 409, unknown → 500) and use it in every route's catch block. Never hand-roll per-route catch logic.
- **Catch as `unknown`,** not `any` or `Error`. Narrow with `instanceof` before touching `.message`.
- **Never forward raw error internals to clients.** Stack traces, ORM metadata, third-party API internals — log them server-side, return a sanitized code.
- **Use a structured error envelope:** `{ error: { code, message, details? } }`. A stable machine-readable `code` lets clients branch without string-matching human copy.

## 2. Readability

Readability standards make the codebase legible at a glance and minimize reviewer cognitive load.

### 2.1 File Naming

- **Pick one case convention and enforce it.** `kebab-case` for files is a common, friction-free default (`api-utils.ts`, `use-job-poller.ts`). Whatever you pick, the linter enforces it.
- **Hooks are prefixed `use-`** and live together (`use-items.ts`).
- **Tests are colocated predictably** — either next to the source (`foo.test.ts` beside `foo.ts`) or under a mirror tree. Pick one; §7.3 details a mirror layout.
- **Framework files follow the framework's conventions** (e.g. `route.ts` / `page.tsx` / `layout.tsx` in Next.js App Router).

### 2.2 Function and Component Size

- **Keep functions small (~30 lines as a soft target).** Extract helpers as complexity grows. It's a guideline, not a hard gate — don't split a coherent 35-line function just to hit a number.
- **Functional components and hooks only.** No class components.
- **Server Components by default** (in frameworks that support them). Add `"use client"` only when you need state, effects, refs, browser APIs, event handlers, or context.

### 2.3 Imports

- **Use a path alias for app-internal imports** (`@/` → `./src/`). No deep relative chains — `../../../lib/foo` is a smell.
- **Use workspace/package aliases for shared code** (`@yourscope/ui`, `@yourscope/database`).
- **Group imports** consistently: external packages → internal/shared packages → local aliases. A lint rule (`import/order`) can enforce and auto-fix this.

### 2.4 Comments and Documentation

- **Comments explain *why*, not *what*.** The code already says what it does.
- **JSDoc public utilities with non-obvious semantics** — surface gotchas and edge cases, not the obvious signature.
- **No commented-out code.** Delete it; version control remembers.
- **When deprecating, point to the replacement** in the JSDoc. Don't mark something `@deprecated` with no migration path.

### 2.5 Visual Style

- **Theme via design tokens, not hardcoded values.** Use semantic CSS variables / Tailwind theme tokens (`bg-primary`, `text-muted-foreground`, `border-border`) — never ad-hoc `bg-blue-500` or raw hex in components.
- **Merge classes with a helper** like `cn()` (`clsx` + `tailwind-merge`) so conflicting utility classes resolve predictably.
- **Dark mode is first-class.** If you support it (class-based is the common approach), every component must work in both modes — verify by toggling, don't assume.

### 2.6 Date and Currency Formatting

- **Route all user-facing dates through shared formatters** (`formatDate` / `formatDateTime` / `formatRelativeTime`) backed by `Intl.DateTimeFormat`. Never call `.toLocaleString()` directly in a component — centralizing makes it testable and locale-consistent.
- **Route all money through one `formatCurrency` helper** that handles whatever numeric types your data layer emits (number, string, decimal) uniformly.

## 3. Consistency

Consistency standards eliminate "two ways to do the same thing." When there's a sanctioned pattern, use it.

### 3.1 The API Route Template

Every route handler follows one skeleton. The order is non-negotiable: **auth → tenant/authorization scope → validate → business logic → respond → centralized error handler.**

```ts
export async function POST(req: Request) {
  try {
    const session = await getSessionUser();          // 1. Authenticate
    const tenantId = getTenantId(session);           // 2. Scope / authorize
    const body = await req.json();
    const parsed = createThingSchema.parse(body);    // 3. Validate
    const thing = await db.thing.create({            // 4. Business logic
      data: { tenantId, ...parsed },
    });
    return jsonResponse(thing, 201);                 // 5. Respond
  } catch (error: unknown) {
    return handleRouteError(error);                  // 6. Centralized errors
  }
}
```

Skipping steps 1 or 2 is a security incident waiting to happen. Different surfaces (admin vs. user, internal vs. public) may use different auth helpers, but the *shape* is identical everywhere.

### 3.2 The Data-Hook Template

Every data-fetching hook follows one pattern, built on your query library:

```ts
"use client";
import { useQuery } from "@tanstack/react-query";
import { apiFetch } from "@/lib/api-client";
import { queryKeys } from "@/lib/query-keys";

export function useThings(params: Record<string, string>) {
  return useQuery({
    queryKey: queryKeys.things.list(params),
    queryFn: ({ signal }) => apiFetch<ThingsResponse>("/api/things", params, signal),
  });
}
```

Mutations use optimistic updates with rollback (`onMutate` snapshot → `onError` restore → `onSettled` invalidate).

### 3.3 Centralized Query Keys

- **All query keys come from one factory** (`@/lib/query-keys`). Never hand-write `["things", "list", ...]` inline. Expose `all`, `list(params)`, and `detail(id)` per resource so invalidation is reliable and hierarchical.
- **Serialize param objects deterministically** — e.g. `JSON.stringify(Object.entries(params).sort())` — so `{a,b}` and `{b,a}` don't become two cache entries.
- **Never use a raw URL string as a query key.** Structured arrays only.

### 3.4 Centralized Helpers — Don't Re-Invent

Maintain a known home for cross-cutting concerns and import from it rather than re-implementing. A typical table:

| What you need | Where it lives |
|---|---|
| Auth + tenant scope | `getSessionUser`, `getTenantId`, role checks — `@/lib/api-utils` |
| Error / response builders | `errorResponse`, `jsonResponse`, `handleRouteError` — same |
| Class merging | `cn()` — `@/lib/utils` or your UI package |
| Date / currency formatting | `@/lib/utils` |
| Query keys | `@/lib/query-keys` |
| The data-store client | a single shared singleton — never instantiate a new client per module |

If you're writing one of these from scratch, stop and import the existing one. If it's missing a feature, extend it — don't fork it.

### 3.5 Role and Permission Checks

- **One sanctioned helper for elevated-permission checks** (`isAdminOrOwner(role)`). Never inline `["owner","admin"].includes(role)` at call sites — a single helper means a single place to change the policy.

### 3.6 State Machines and Status Transitions

- **Model lifecycle status as an explicit state machine.** Define the legal transitions in one place; forbid skipping states. Don't let arbitrary code assign `status` directly.
- **Record every transition** through one helper (e.g. append to a status-history log) so the audit trail is automatic, not something each call site remembers to do.

### 3.7 Constants Live in One Place

- **Name your magic numbers and strings.** Statuses, limits, dimensions, pricing, feature thresholds — anything with meaning lives in a `constants/` module, not inline in business logic.

## 4. Modularity

Modularity standards govern code organization, dependency direction, and separation of concerns.

### 4.1 Monorepo / Package Boundaries

If you use a monorepo (Turborepo, Nx, pnpm workspaces):

- **A `database`/`data` package** owns the schema, the singleton client, and shared queries. Apps consume it; apps never instantiate their own client.
- **A `ui` package** owns shared primitives (`Button`, `Card`, `Input`) and `cn()`. App-specific UI stays in the app.
- **A `tsconfig` package** owns the shared base configs. Apps extend, never override `strict`.
- **An `eslint-config` package** owns the shared lint rules.

The dependency direction is **apps → packages, never the reverse.** Packages must not import from apps. A single-app repo applies the same idea at the folder level: feature folders depend on shared `lib/`, not on each other.

### 4.2 The DRY Threshold

- **Extract when the same logic appears in 2+ places.** Two duplications is the trigger; one is fine.
- **Don't extract speculatively.** A "might be useful later" helper used in exactly one place is dead weight.
- **Scope extraction to need:** shared by multiple apps → a package; needed by one app → that app's `lib/`.

### 4.3 Server/Client Boundaries

- **Server Components by default;** add `"use client"` only when the component genuinely needs the client runtime.
- **Components that rely on client-only features** (e.g. `next/dynamic` with `ssr: false`, browser APIs) must declare `"use client"` at the top.
- **Server code must not import client-only modules** (hooks, `window`, event handlers), and vice versa. Keep the boundary clean — a shared util imported by both sides must be isomorphic.

### 4.4 The `lib/` Layout

Partition `src/lib/` **by domain, not by technical layer.** For example: `auth/`, `email/`, `validations/`, `constants/`, plus one folder per integration or bounded context. Cross-domain shared utilities (`api-utils.ts`, `utils.ts`, the data client) sit at the top of `lib/`. Domain folders import from the top-level shared utils, never reach sideways into each other.

### 4.5 Integration Encapsulation

- **Every third-party API lives behind one module.** All calls to a given external service (payments, email, a vendor API) go through a single `lib/<service>/` layer. Nothing outside it calls the vendor SDK directly — that's the only place to add retries, logging, rate-limit handling, and types.
- **Long-running external calls run in a background job,** not inline in a request. Enqueue a job row, process it in a worker; request handlers never block on slow third-party calls beyond a quick lookup.
- **Shared type definitions (e.g. `JobType`) live in one place** — never duplicated between the enqueue side and the worker side.

### 4.6 The Background Worker

If you run a worker:

- **One entrypoint, a bounded poll/consume loop**, and **one processor registered per job type.** Unknown job types fail fast rather than crashing the loop.
- **Each job is instrumented** (a trace span per job) and **idempotent** (see §6.8) so restarts are safe.
- **Graceful shutdown** drains in-flight work on SIGTERM.
- **Worker code is tested and counted in coverage** — it's not a second-class citizen.

### 4.7 Domain Encapsulation

- **Keep domain rules in closed systems.** Categorization rules, fee tables, packing/allocation algorithms — each lives in its own module with a clear interface. Don't hardcode a domain constant (a fee, a limit, a category) inline in a component; import it from the owning module so there's exactly one source of truth.

## 5. Security

Security standards are non-negotiable. Each carries a "blast radius": violating it can leak data, expose credentials, or bypass authentication.

### 5.1 Authentication is Mandatory

- **Every API route authenticates before any business logic** — a single `getSessionUser()`-style call is what stands between an attacker and your data. No exceptions.
- **Every multi-tenant route then resolves and applies the tenant scope.** Skipping that line is the highest-severity bug class in a multi-tenant app.
- **Privileged surfaces (admin) require an explicit elevated-role check** in their own auth helper.

### 5.2 Page Routes Must Be Protected

- **Every new authenticated page is registered with the route guard** (middleware allow/deny list, layout-level auth check, or framework equivalent). The guard redirects unauthenticated users to login. A page that forgets to register is silently public.
- **Document the deliberate exceptions** (e.g. a billing page reachable while locked out) so "unprotected" always means "intentionally public."

### 5.3 Tenant / Data Isolation

- **Every tenant-scoped query includes the tenant key.** There is no situation in which one tenant should see another's data.
- **Aggregate/admin surfaces return aggregates only** when they're meant to — counts, sums, percentiles — and never leak raw PII or per-tenant identifiers unless that's the explicit purpose of the endpoint.
- **Keep cross-tenant/admin queries in one reviewable module** so the isolation rules are auditable in one place.

### 5.4 Secrets and Tokens

- **Hash tokens before storage.** For magic links, invites, API keys, password-reset tokens: send the raw token to the user, store only its hash (SHA-256). A database leak then exposes nothing usable.
- **Compare secrets in constant time.** Use `crypto.timingSafeEqual` (length-check first, then compare) for HMAC/signature/token comparison — never `===`/`!==`, which leak length and content via timing.
- **Bake expiry into signed tokens** and validate it before the signature check.
- **Never commit secrets** — no `.env` with real values, no keys, no auth artifacts. Use a secrets manager in production and `.env.local` in development. Commit only `.env.example`.

### 5.5 Input Validation and Output Sanitization

- **Validate every request body with a schema** before business logic (§1.3).
- **Validate every URL fetched server-side** — enforce HTTPS and an expected host allow-list before calling `fetch`. Webhook/callback URLs are a classic SSRF vector.
- **Never `dangerouslySetInnerHTML`** with untrusted input. If you must render HTML, sanitize with DOMPurify (or equivalent) and get a second review.
- **Never forward raw error internals to clients** (§1.5).

### 5.6 Rate Limiting and Replay Prevention

- **Rate-limit auth endpoints** (login, magic links, invites, password reset). Check for a recent outstanding token before issuing a new one.
- **Short-lived, single-use tokens.** Expire them on a tight window and mark consumed (or delete) on use.

### 5.7 Test-Mode Endpoints

- **Gate test/back-door endpoints with positive opt-in,** e.g. `APP_ENV === "e2e"` — never negative opt-out like `NODE_ENV !== "production"`. Default-deny: a misconfigured deploy should fail closed, not expose a test-signin route in prod.

### 5.8 Dependencies

- **Prefer lightweight, well-maintained libraries;** check whether an existing dependency already covers the need before adding a new one.
- **Pin overrides** for transitive deps with known vulnerabilities, and remove the pin when upstream fixes it.
- **Restrict install-time build scripts** to the packages that genuinely need them (e.g. pnpm's `onlyBuiltDependencies`). Adding to that list is a reviewed decision.
- **Run dependency audits in CI** and triage findings; don't let the backlog grow silently.

## 6. Reliability

Reliability standards govern behavior under load, failure, and concurrency.

### 6.1 Performance Defaults

- **Parallelize independent async work** with `Promise.all`. Sequential `await`s for unrelated calls is a code smell.
- **Aggregate in the database,** not in JS (§1.4).
- **`select` only needed columns;** paginate every list (§1.4).

### 6.2 Query-Cache Tuning

- **Set `staleTime` by data volatility:** ~30s for dashboards/feeds, ~60s+ for billing/financial data, ~5min for settings/config.
- **Expose `staleTime` / `gcTime` / `queryKey` through hook options** — different consumers want different freshness; don't bake one global default into every hook.
- **`useMemo` for column definitions, expensive computations, and object/array props** — referential churn cascades into re-renders.
- **Optimistic mutations** use snapshot → rollback (`onMutate`/`onError`/`onSettled`).

### 6.3 Heavy Client Bundles

- **Lazy-load heavy client-only libraries** (charts, editors, maps) with dynamic import + `ssr: false`. Pages doing this declare `"use client"`.
- **Import individual icons/utilities,** never an entire pack — let tree-shaking work.

### 6.4 Background Jobs and Polling

- **Every polling loop has a maximum iteration count** (e.g. 60 ticks at 5s = 5 min). Unbounded polling leaks resources and hammers the server.
- **Clean up intervals on unmount and on tab-visibility change;** resume on visibility restore if the operation is still in flight. Centralize this in one `useJobPoller`-style hook rather than re-deriving the effect/ref boilerplate.
- **Run long operations in the worker,** never inline in a request (§4.5).
- **The worker is fault-tolerant:** failed jobs are caught, logged, and marked failed; unknown types fail explicitly rather than crashing the loop.

### 6.5 Fallback to Cached Data

- **Prefer returning stale cached data with a background refresh** over blocking a render on a slow external call. A slow vendor API should never freeze a dashboard.

### 6.6 Observability Hooks

- **Capture exceptions at boundaries** where you catch and swallow (§12).
- **Wrap long-running operations in trace spans** so latency and failures are searchable.

### 6.7 Migrations and Schema Changes

- **Migrations are forward-only.** Never edit a committed migration — create a new one.
- **Regenerate the client and verify every consumer builds** after a schema change.
- **Backwards-compatible, multi-pass changes for in-flight deploys.** To drop a column: stop writing it in one deploy, drop it in the next. Never break a running version mid-rollout.

### 6.8 Idempotency

- **Webhooks must be idempotent** — dedupe on the provider's event ID with a unique constraint to swallow redeliveries.
- **Job processors must be idempotent** — a worker can die and restart mid-job; partial work must be safe to redo.

### 6.9 Graceful Degradation

- **Feature-detect optional capabilities** (camera, clipboard, notifications, hardware). When the API is unavailable, degrade to a manual path rather than throwing. These paths are often excluded from coverage thresholds because the test environment can't simulate them — document why when you exclude them.

## 7. Testing

Testing standards govern coverage targets, structure, mocking, and the unit/E2E split.

### 7.1 Coverage Thresholds (Enforced)

- **Set and enforce per-target thresholds** in the test runner so a drop fails the build. Sensible defaults:

| Layer | Lines | Functions | Branches | Statements |
|---|---|---|---|---|
| Backend / server | 90% | 90% | 85% | 90% |
| Frontend / UI | 80% | 80% | 75% | 80% |

- **Also enforce a per-file floor** (e.g. 50%) so one well-tested file can't mask an untested neighbor.
- **Frontend thresholds are often lower than backend** because of unavoidable environment gaps (hardware, complex canvas/DOM). When you exclude a file from coverage, leave a one-line comment explaining *why*.

### 7.2 Required Tests for New Code

- **Every new API route** has, at minimum: unauthenticated (401), forbidden (403, where applicable), happy path, validation error (where there's a body), and a failure case (data-store or external error).
- **Every new hook** is tested for: query-key structure, enabled/disabled conditions, and error handling.
- **Every new worker processor** is tested and counted in coverage.
- **Every user-facing feature** gets E2E coverage in addition to unit tests.

### 7.3 Test Layout

Pick one layout and apply it everywhere. A mirror tree keeps tests discoverable:

```
<target>/
├── src/
│   ├── __tests__/          # Unit tests, mirroring src/
│   │   ├── setup.ts         # Setup/mocks/fixtures live at the top,
│   │   ├── mocks/           #   as siblings of the mirror dirs
│   │   ├── lib/             # mirrors src/lib/
│   │   ├── components/      # mirrors src/components/
│   │   └── ...
│   ├── lib/
│   └── components/
└── tests/                  # E2E only — never under src/
```

- Unit tests mirror `src/`. The test for `src/lib/utils.ts` is `src/__tests__/lib/utils.test.ts`.
- Test infrastructure (setup, mocks, fixtures) sits directly under `__tests__/`, not inside a mirror dir.
- E2E tests live at the project root `tests/`, never under `src/`.
- Test files are named consistently (`*.test.ts(x)` for unit; `*.spec.ts` for E2E, if you separate them). Don't mix conventions within a layer.

### 7.4 Mocking Strategy

- **Mock the data-store client globally** and reset it between tests, so unit tests never hit a real database.
- **Mock auth globally** with a small set of named helpers (`mockAuthedUser`, `mockUnauthenticated`, `mockForbidden`, …) so each test states its auth posture in one line.
- **Provide a request builder** (`createRequest(method, url, body?, params?)`) for route-handler tests instead of constructing request objects by hand.
- **When mocking a custom error class,** set the discriminating field your error handler checks (e.g. `this.name = "ApiError"`) so the mock takes the same branch as the real thing.

### 7.5 Test Style

- **Backend tests run in a Node environment,** calling the handler directly with a synthetic request — no HTTP server, no real DB.
- **Frontend tests run in jsdom** with React Testing Library. Test behavior, not implementation.
- **Query by role and accessible name** (`getByRole`, `getByLabelText`, `getByText`). Avoid CSS selectors and `data-testid` unless there's no semantic alternative.
- **Use `waitFor` for async assertions** — never `await new Promise(r => setTimeout(r, N))`.
- **Use fake timers** (`vi.useFakeTimers()` + `advanceTimersByTimeAsync`) for time-dependent logic. Real `setTimeout` makes tests slow and flaky.
- **Every test starts from a clean state** via a global `beforeEach` reset; each test sets up its own returns.

### 7.6 E2E Tests

- **E2E tests run against an isolated, ephemeral database — never a shared dev or staging DB.** Locally, route runs through a script that spins up a disposable Postgres (or equivalent) per run, ideally namespaced per process so parallel runs from different branches/worktrees can't collide. **Don't invoke the E2E runner directly against whatever `DATABASE_URL` your shell happens to have** — that's how branches corrupt each other's data. There is no "just one quick test" exception.
- **CI is the place direct invocation is fine,** because CI provisions a dedicated ephemeral database per job — the cross-pollution risk doesn't exist there.
- **Mutation tests run after read-only tests,** not interleaved, to avoid data races. Read-only suites can parallelize freely.
- **Run an RTL/a11y pass** as its own project if you support multiple directions/locales (§8, §9).
- **Authenticate once** via a setup project that writes a reusable storage state, consumed by all subsequent specs.
- **No hardcoded `setTimeout` in E2E** — use the framework's `waitFor`/auto-waiting. Set sane global action/expect timeouts and don't override them per-test without reason.

### 7.7 Verification Before "Done"

Before claiming a feature complete:

1. **Lint** — zero errors, zero warnings.
2. **Build** — zero errors, zero warnings.
3. **Unit tests** for every target you touched.
4. **E2E tests** for any user-facing change.

If any step warns, fix it and re-run until output is clean. "It probably works" is not "done."

### 7.8 Accessibility Tests

- **Run an automated a11y audit** (axe-core via `jest-axe` / Playwright's `@axe-core/playwright`) before merging UI changes to shared components — and run the RTL pass for layout changes. Automated checks catch ~30% of issues; the rest need a human (§9.7).

## 8. Internationalization & Localization

Apply this section if your app is (or may become) multilingual. Even single-language apps benefit from never hardcoding user-facing strings.

### 8.1 Locale Support

- **Declare supported locales in one place;** mark which are RTL.
- **Locale lives in the URL path** (`/[locale]/...`) so it's linkable, cacheable, and SSR-friendly. A guard/middleware handles defaulting and redirects.
- **One message catalog per locale,** identical key trees. Missing keys fall through to the default at runtime, but the translation pipeline keeps them in sync.

### 8.2 Translation Workflow

- **Never hardcode user-facing strings.** Every visible string goes through the i18n layer (`useTranslations()` client / `getTranslations()` server). Hardcoded copy in JSX is a regression.
- **Namespace keys by feature** with dot notation (`Shipments.actions.create`).
- **Use ICU MessageFormat for plurals and interpolation** — `{count, plural, one {# item} other {# items}}` — never string concatenation, which breaks word order across languages.
- **Pluralization is per-locale** (some languages have up to six plural forms). Don't assume English's two-form rule.
- **Format dates and numbers via `Intl.*`** (wrapped in your shared formatters), never `toLocaleString()` inline.

### 8.3 RTL Support

- **One sanctioned RTL detector** (`isRtlLocale` / `getDirection`); never compare locale strings inline.
- **Use logical CSS utilities** (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`) instead of physical (`ml-*`, `pl-*`, `left-*`) — logical properties flip automatically.
- **Direction-implying icons** (chevrons, arrows, back buttons) flip in RTL (`rtl:rotate-180` or equivalent).
- **Test in both directions.** Adding a layout-heavy component without an RTL test is a review blocker.

### 8.4 Locale Persistence

- **Persist the user's preferred locale** (on the session/profile) and honor an explicit in-session override (a `NEXT_LOCALE`-style cookie) before falling back to the preference.

### 8.5 UI Text Capitalization

- **Sentence case for short UI copy** — titles, buttons, menu items, headers, labels under ~5 words. Capitalize only the first word plus proper nouns and acronyms (`Sign out`, not `Sign Out`).
- **Preserve acronyms, codes, and brand names** (`SKU`, `USD`, `Apple Pay`).
- **Longer descriptive copy** keeps normal sentence punctuation.
- **Legal documents are exempt** — keep defined legal terms as authored.

## 9. Accessibility

Accessibility is non-negotiable, user-facing quality. Inaccessible UI ships bugs to anyone using a screen reader, keyboard, switch, or voice control.

### 9.1 Semantic HTML First

- **Use the right element:** `<button>` for actions, `<a>` for navigation, `<form>` for input, `<h1>`–`<h6>` in document order. A `<div onClick>` is not a button.
- **One `<h1>` per page;** headings descend monotonically — don't jump `<h2>` → `<h4>`.
- **Use landmark regions** (`<main>`, `<nav>`, `<aside>`, `<header>`, `<footer>`) so screen-reader users can skim.

### 9.2 Forms and Labels

- **Every field has an associated label** — explicit `<label htmlFor>` or `aria-label`/`aria-labelledby`. Placeholder text is not a label.
- **Validation errors are programmatically associated** via `aria-describedby` and announced (`role="alert"` / `aria-live="polite"`).
- **Required fields** use `aria-required` plus a visible marker (with `aria-hidden` on a decorative asterisk).

### 9.3 Dialog/Sheet Description Requirements

- **Modal primitives (`Dialog`, `Sheet`, `AlertDialog`) include a description element,** even if `sr-only`. Component libraries (Radix and others) warn when it's missing and screen readers lose context. This is a frequently-violated rule — check it in review on every modal PR.
- **Tooltips are reachable on focus,** not hover-only.

### 9.4 Keyboard Navigation

- **Every interactive element is keyboard-reachable** in tab order with a visible focus ring. Don't kill focus outlines without a custom replacement.
- **Modals trap focus correctly** (Tab wraps last→first, Shift+Tab first→last). Library primitives handle this; custom modals must replicate it.
- **Honor conventions:** Escape closes, Enter submits, arrows navigate menus/tabs.
- **Provide skip links** ("Skip to main content") on layouts with heavy nav chrome.

### 9.5 Color and Contrast

- **Meet WCAG AA contrast** (4.5:1 normal text, 3:1 large). Tune your token palette for it; don't introduce ad-hoc colors that violate it.
- **Never convey meaning by color alone** — pair status colors with an icon, label, or shape.
- **Both light and dark modes** meet contrast independently.

### 9.6 Images and Media

- **Every `<img>` has `alt`.** Decorative images use `alt=""` (present, empty); informative images describe what they convey.
- **Icon-only buttons** get an accessible name via `aria-label`.

### 9.7 Automated and Manual Checks

- **Run an automated a11y suite** for the common regressions.
- **Manually screen-reader test** (VoiceOver / NVDA) significant UI work before merge — automation catches ~30%; a human catches the rest.
- **Run the RTL pass** for layout changes (§8.3).

## 10. Git & Version Control

Git standards govern commit hygiene, branch policy, and the safety nets that keep the main branch shippable.

### 10.1 Conventional Commits

- **Follow [Conventional Commits](https://www.conventionalcommits.org),** enforced by commitlint in a `commit-msg` hook. Format: `<type>(<scope>)?: <description>`.
- **Allowed types:** `feat`, `fix`, `refactor`, `chore`, `test`, `docs`, `style`, `perf`, `build`, `ci`, `revert`.
- **Subject ≤ ~100 chars; body wraps at 72.** Use the body to explain *why*, not what (the diff shows what).
- **Reference issues** in the body/footer (`Refs: #123`, `Fixes: #456`).

### 10.2 Pre-Commit Hooks

Wire a few layers of safety with Husky (or equivalent):

1. **`pre-commit`** runs lint-staged (ESLint `--max-warnings 0` + formatter on changed files) and a typecheck, plus targeted tests for changed files (`vitest related --run`).
2. **`commit-msg`** runs commitlint.

### 10.3 Hook Bypass Policy

- **Never `--no-verify` to skip a failing hook.** If a hook fails, fix the cause. The only defensible exception is a confirmed secret-scanner false positive that can't be refactored away — note it in the PR.

### 10.4 Branch and Merge Policy

- **`main` is the long-lived integration branch;** all work merges via PR.
- **Feature branches are short-lived** (target: under a week). Rebase onto `main` regularly.
- **Squash-merge noisy branches;** keep merge commits when intermediate history tells a useful story.
- **Force-push to feature branches is fine; force-push to `main` is forbidden.** Never rewrite `main`'s history.

### 10.5 What Not to Commit

- **`.env*` beyond `.env.example`** — never secrets, even temporarily.
- **E2E auth/storage state, coverage, build output, `node_modules/`** — anything gitignored.
- **Generated client/code** (ORM clients, codegen output).
- **Personal IDE settings** not shared by the team.

## 11. CI/CD & Deployment

CI/CD standards keep `main` deployable and production stable.

### 11.1 The CI Pipeline

On every PR, run these jobs (in parallel where possible):

1. **Lint** — install with a frozen lockfile, then lint. Fail on any error.
2. **Audit** — dependency vulnerability scan (advisory until the backlog is clean).
3. **Build** — provision a throwaway database, run migrations + codegen, then build. Catches type and build errors.
4. **Unit tests** — per target; fail on dropped coverage thresholds.
5. **E2E** — sharded across parallel matrix runs; each shard provisions its own ephemeral database. Upload reports/traces as artifacts on failure.

**Lint, build, all unit jobs, and all E2E shards must pass before merge** — enforced by branch protection. Audit is advisory. A concurrency group cancels superseded runs on the same ref so force-pushes don't stack runners.

### 11.2 Deployment Environments

- **Define each environment explicitly** (production, staging, local) and what backs it (compute, database, secrets store). Document them so "where does this run" is never a guess.
- **Local mirrors CI's database image** (e.g. the same Postgres version) so behavior matches.

### 11.3 Deploy Gating

- **Production deploys trigger on a deliberate signal** (a `v*` tag, a release, a protected-environment approval), not on every push to `main`.
- **Verify the deploy target is an ancestor of `main`** so a tag pushed from a feature branch can't ship.
- **Re-run CI against the exact deployed commit;** all checks pass on that commit, not just on the PR.
- **A concurrency group prevents racing production deploys.**
- **Have a tested rollback path** — re-deploy a previous immutable image tag via a one-click workflow. Retain the last N images.

### 11.4 Build Artifacts

- **Frozen lockfile everywhere** — CI never mutates it.
- **Pin the toolchain** (Node version, package-manager version) at the workflow level.
- **Run migrations as a one-shot step before services roll,** not per-container at boot (which races across replicas and can crash-loop a service).
- **Immutable image tags** (`<git-tag>-<sha>`) — no service follows a moving `:latest`.
- **Pass build-time secrets via secret mounts,** never as build args that land in image history.
- **Post-deploy smoke test** — hit a health endpoint that exercises a real dependency (e.g. `SELECT 1`) after the rollout reports stable.

### 11.5 Local Verification Mirrors CI

- **Run lint, build, and the relevant unit/E2E targets locally before opening a non-trivial PR.** The same checks CI runs, run first on your machine.

## 12. Observability & Logging

Observability standards make production issues debuggable without a redeploy.

### 12.1 Error Tracking

- **Wire an error tracker** (Sentry or equivalent) into every runtime layer — client, server, edge, and any worker — each with its own init.
- **Instrument long-running operations with trace spans** named consistently (`worker.job.<type>`, `op: "job.process"`, with searchable attributes) so you can filter by operation and find slow/failing ones.
- **Capture exceptions explicitly at boundaries where you swallow errors.** If your centralized handler never sees the error, the tracker doesn't either.
- **Scrub PII before sending.** A `beforeSend` hook drops sensitive headers (`authorization`, `cookie`, signatures), drops raw request bodies, and strips/redacts emails, names, and IDs from messages. Never disable it. Put identifiers in tags/contexts (where the scrubber is configured), not in error message strings.
- **Sample by operation:** critical paths (jobs, auth, webhooks) at 1.0; chatty background work low (0.1); everything else in between.

### 12.2 Logging Conventions

- **Tag every log line with a prefix** so production search is feasible: `[worker]`, `[api]`, `[<service>]`.
- **Don't double-log.** If your centralized error handler already logs, don't log the same error again in the catch block.
- **Never log request bodies, query params, or response bodies** without sanitization — they contain user data.
- **Prefer structured logging** — pass objects, not concatenated strings, so aggregators can parse fields: `log("[worker] job complete", { jobId, type, durationMs })`.

### 12.3 Health and Metrics

- **Liveness probes are unauthenticated and thin** — `/api/health` returns `{ status: "ok" }`. Load balancers hit these; don't break them without coordinating an infra change.
- **Keep authenticated metrics endpoints separate** from liveness probes, even if the names are similar. Never point a load balancer at a dashboard endpoint.

### 12.4 Tracing

- **Enable distributed tracing across browser → server → worker.** Don't strip trace-propagation headers (`sentry-trace`, `baggage`, or your tracer's equivalent) when forwarding requests.

## 13. Configuration & Environment

Configuration standards prevent "works on my machine" and "we shipped staging credentials to prod."

### 13.1 Environment Variable Discipline

- **Validate env vars at startup or first use** with an early guard that throws a clear error when a required var is missing. Don't assume they exist. A schema (Zod) over `process.env` at boot is a clean pattern.
- **No non-null assertions on `process.env.X!`** in production paths (§1.1).
- **Public client-side vars carry the framework's public prefix** (`NEXT_PUBLIC_`, `VITE_`, …). Anything without it is server-only and must never reach a Client Component.
- **`.env.example` is the source of truth** for which variables exist — update it whenever you add one. Never commit real `.env` files.

### 13.2 Per-Environment Behavior

- **Use a dedicated `APP_ENV` for app-level environment distinctions** (test-mode features) with positive opt-in (§5.7). Don't repurpose `NODE_ENV`, which is for build/runtime mode (`development`/`production`/`test`).
- **Required secrets** (`DATABASE_URL`, auth secrets) are validated; CI sets dummy values for jobs that don't need a real backend.
- **Production secrets live in a secrets manager,** injected at boot. Never hardcode them in IaC or Dockerfiles.

### 13.3 Feature Flags

- **Don't add a general-purpose flag system speculatively.** Gate a hidden feature on `APP_ENV` or a per-tenant setting.
- **Don't flag unshipped code indefinitely** — ship it or delete it; half-shipped code rots.
- **Don't gate bug fixes behind flags** — fixes ship to everyone.

### 13.4 Configuration Files

Keep one canonical config per concern and **don't fork them across apps** — propagate a needed setting to all apps rather than letting them drift. Typical set: workspace manifest, task-runner config (Turbo/Nx), ESLint config, commitlint config, base `tsconfig`, framework config, test config (with coverage thresholds), and the design-token/theme config.

## 14. Documentation

Documentation standards keep the codebase navigable for new contributors and future-you.

### 14.1 Canonical Documents

| File | Audience | Purpose |
|---|---|---|
| `README.md` | New contributors | What is this, how do I run it |
| `CLAUDE.md` / `AGENTS.md` | AI agents + contributors | Normative coding rules, architecture, domain models |
| `STANDARDS.md` | Everyone | Long-form standards (this document) |
| `CHANGELOG.md` | Everyone | User-visible changes per release |
| `docs/` | Engineers | Specs, audits, roadmap |

When normative documents disagree, define an explicit precedence order and state it at the top of each.

### 14.2 Code Documentation

- **JSDoc public utilities with non-obvious semantics** — the signature is self-documenting; the JSDoc explains *why* and surfaces gotchas.
- **Inline comments explain *why*,** not *what*.
- **No commented-out code** — delete it; git remembers.
- **No `TODO:` without an issue reference** — a TODO with no tracker rots. Fix it, file it, or delete it.

### 14.3 Feature / Spec Docs

- **Multi-step features get a spec before implementation** under `docs/`. Keep audits alongside, and maintain a roadmap and a doc index.

### 14.4 Updating This Document

- **These standards are normative.** Change them when standards change — not after the fact. A PR that violates a standard either fixes the violation or amends the standard, with a note explaining why.
- **Keep examples current.** A stale reference is worse than no reference.
